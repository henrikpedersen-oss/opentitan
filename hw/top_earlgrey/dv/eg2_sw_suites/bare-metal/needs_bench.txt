# Tests the model cannot run honestly: their bench sequence does the step the software waits for,
# or their checks measure something the model does not have (clock frequencies). run.sh reports them as
# model-stop with the reason below, without running them: setting the value the software waits
# for, or passing a measurement of nothing, would make the software pass without what the test
# exists for. They run on the chip bench. One line per test: <regular expression for the test
# name> <the reason>.
example_mem_ujcmd_test            test finding: the sim_dv image reads uJSON from the OTTF console, which ottf_main.c does not initialise for kDeviceSimDV, so it jumps to address 0 before any host byte (ticket "example_mem_ujcmd: the sim_dv image calls a null console getc"); the model's uJSON host (host.program=example_mem_ujcmd) is ready for an image that reads the console
alert_handler_lpg_sleep_mode_alerts_test  undocumented: the test programs PING_TIMEOUT_CYC_SHADOWED = 256 alert-handler cycles and expects no ping failure, while the model gives the AON alert senders (200 kHz) a three-cycle handshake in their own clock, longer than that; alert_handler.hjson recommends "the equivalent of 256 cycles of the slowest alert sender clock domain" and no document gives the handshake time across clocks (status/dv_tickets.md "alert handler: ping handshake time of the AON alert senders"). The bench part (the alert, kExpectedAlertNumber) is in bench.txt.
alert_handler_lpg_sleep_mode_pings_test  model gap and undocumented: eg2sim's alert handler has no ping testing yet (theory_of_operation.md "Ping Testing", "LFSR Timer", the LPG ping bypass; the bench only forces the ping wait mask to 7), and phase 2 also expects ordinary alert causes from a 2-cycle PING_TIMEOUT_CYC, which no document explains (status/dv_tickets.md "alert handler: ordinary alerts from a too-short ping timeout")
ast_clk_outs_test                 undocumented: after a deep sleep the test requires every clock measurement disabled, MEASURE_CTRL_REGWEN back to 1 and RECOV_ERR_CODE kept; no clkmgr or pwrmgr document gives what low power does to them (the model measures the clocks; its chip sequence only turns assertions off). Ticket "clkmgr: what a deep sleep does to the frequency measurements" (status/dv_tickets.md)
clkmgr_jitter_frequency_test      undocumented: the test needs the jittery main clock to leave the no-jitter thresholds (5%); AST doc/interfaces.md says only "jittery system clock" and clkmgr's JITTER_ENABLE "enable jittery clock": no document gives how far the jittery clock deviates, so the model's main clock does not jitter. Ticket "Clock jitter: how far the jittery main clock deviates" (status/dv_tickets.md)
data_integrity_escalation_reset_test  test finding: after its load or fetch integrity error the test expects the core to run its load-integrity handler and the escalation NMI handler (mtval, NMI_STATE, class phase); Ibex security.rst "Bus integrity checking" gives a bus major alert, rv_core_ibex interfaces.md maps it to fatal_hw_err, and theory_of_operation.md "Local Escalation Path" disables fetch on fatal_hw_err until reset, so no handler runs (status/dv_tickets.md "eg2_fetch_intg expects the core to run on after fatal_hw_err", which covers this test too)
sram_ctrl_scrambled_access_test  test finding: the test reads its pattern back after the key renewal, counts the load integrity errors in its internal-interrupt handler and goes on checking; each integrity error is a bus major alert, fatal_hw_err, and fetch disabled until reset (rv_core_ibex theory_of_operation.md "Local Escalation Path"), so the handler cannot run (status/dv_tickets.md "eg2_fetch_intg expects the core to run on after fatal_hw_err", which covers this test too)
